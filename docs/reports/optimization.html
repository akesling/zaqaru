What changed

01

Repair the measurement foundation

Added checksum validation, completed-work checks, instruction-count comparisons, fresh baked modules, interleaved A/B ordering, raw samples and environment hashes. Fixed the differential reference to disable acceleration. Wrapped local Docker builds, tests and measurements in scripts. Kept all benchmark validation out of CI.

6cdf119 · 57ad2ff · 0cec2b9
02

Make register indices provably safe

Expanded the bytecode interpreter’s local register array from 24 to 32 slots, matching its five-bit operand encoding. The compiler can remove per-operand bounds checks. Only 16 architectural registers are copied back; guest state and bytecode format stay the same.

faf6988 · default engine
03

Specialize the existing interpreter

Used weval to turn constant decoded bytecode and instruction addresses into Wasm functions. Registers, flags, permissions, memory and execution budgets remain dynamic. This reuses the engine’s x86 semantics instead of maintaining a second instruction implementation.

4862b4c · opt-in experiment
04

Compile live continuations in the browser

Ported the evaluator into a Wasm optimizer Block with the two existing StructFS imports. Hot-trace profiling selects up to 32 traces; a frozen source snapshot becomes a specialized successor. Trace identities and a small lookup cache avoid repeatedly comparing whole bytecode buffers.

9b7edb9 · opt-in evolution
05

Remove fallback and transfer costs

Added high-byte ALU lowering for supported AH/BH/CH/DH forms, preserving neighboring bytes and flags. This removed a costly fallback in the mixed workload. Cached compiled trace transfers now stay inside the bytecode runner, returning to the engine when invalidation or other handling is needed.

06

Make experiments reviewable

Added repeatable build and browser/Node scripts, artifact hashes, exact continuation checks and timing that includes the transition. Fixed a browser harness navigation race. Committed each milestone separately.

What did not work

A trace abstraction regressed normal ALU and random-memory execution by 13–15% and was removed. A later six-workload scaffold check still measured a 0.965× geometric mean; normal-build overhead remains unresolved. An early rotate fixture exited before completing its loop, so its timing was rejected and completion checks were added.

A browser-capable path to Assembly evolution

The intended architecture is an optimizer producing generated Wasm executor Blocks, with a controller composing an immutable successor Assembly and explicitly transferring continuation ownership. There are no new host imports and no store that silently replaces a running module.

1 / Observe & freezeProfile live x86 traces, stop the source and capture memory plus mount state.
2 / SpecializeThe Wasm optimizer evaluates known bytecode and emits successor Wasm.
3 / InstantiateCreate a frozen successor with the continuation and existing store interface.
4 / Transfer & resumeRetire the source, activate the successor once and compare completed work.

Implemented: compilation inside Wasm and execution in an actual Chrome Worker, plus Node validation. Executor imports remain env.ll_read and env.ll_write; the compiler Block uses structfs.read and structfs.write.

Still a prototype: the demo drives instances directly. Assembly-managed activation, exclusive controller authority, lineage validation, failure recovery and live external-resource handoff are not implemented. Freeze/resume tokens are bookkeeping, not security capabilities.

Current limits: one optimization generation, compilation while frozen, at most 32 selected traces, a roughly 3.3 MiB compiler and about 595 MiB of guest memory in the fixture. Mobile-browser suitability is untested. AOT/server-side optimization remains useful; optimization available inside the browser has priority.

Correctness evidence

  • 81 CPU unit and bytecode tests passed, including high-byte ALU flags, neighboring-register preservation and fault behavior.
  • 560 specialization comparisons covered registers, flags, RIP, retired work, memory, faults, deferral, budgets and dirty code across the four fixtures.
  • Four artifact tests passed for import remapping, duplicate imports, snapshot replacement and unsupported globals.
  • Browser and Node checks passed for matching output, process state, instruction counts, compiled execution, frozen refusal and one-time activation.
  • Hardware lockstep validation failed at PTRACE_GETREGS under local amd64 Docker. Native x86 performance and full x86 specialization correctness remain unverified.

What must happen next

  1. Reduce cross-trace state traffic. Call-heavy code has nearly complete compiled coverage but remains below 2×. The new transfer loop still spills machine state between compiled functions.
  2. Make transitions safe and economical. Implement the Assembly controller and recovery path, measure compilation payback, and handle changing hot code across generations.
  3. Broaden end-to-end evidence. Measure diverse OCI images, startup, steady execution and request latency separately, including compilation and all regressions.
  4. Recheck ordinary execution. Resolve scaffold overhead and validate on native x86-64 when available. Local Docker remains the working environment.

Language-runtime replacement and Python-specific fast paths remain out of scope. Supplemental Python rootfs runs stopped at the existing unsupported sysinfo syscall; no Python or Django gain is claimed.

Reproduce and inspect

Run from the repository root. These are manual tools; no benchmark CI was added to the final branch.

# Saved baseline/candidate comparison and correctness checks
./tools/microbench/experiment.sh ab --repeats 5
./tools/microbench/experiment.sh test

# Four specialized engine fixtures
./tools/microbench/specialize.sh

# Browser continuation (prepare sources and dependencies first)
bash tools/evolution/run.sh prepare /path/to/structfs
bash tools/evolution/run.sh build mixed 100000000
bash tools/evolution/run.sh browser
# Alternatives: build calls 40; run.sh node

A/B requires previously saved baseline and candidate executables. The preparation step downloads pinned dependencies; Chrome is required for the browser harness.
